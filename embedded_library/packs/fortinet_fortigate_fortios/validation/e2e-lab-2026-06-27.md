## Observed blocker

The pack script reached fixture replay but `openssl s_client` failed while writing to the declared TLS listener:

```text
Splunk TEST: http://127.0.0.1:18000
SC4S Fortinet FortiGate/FortiOS TLS listener: 127.0.0.1:20032
write:errno=104
```

A follow-up listener inspection inside the SC4S container showed that only the health endpoint was listening; no syslog-ng listener was bound on TCP/20032:

```text
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address           State       PID/Program name
tcp        0      0 127.0.0.11:46389        0.0.0.0:*                 LISTEN      -
tcp        0      0 0.0.0.0:8080            0.0.0.0:*                 LISTEN      135/python3
```

The SC4S log excerpt available from the container showed startup reached the health service and then `starting syslog-ng`, but syslog-ng was not present in the process table when inspected:

```text
sc4s version=3.44.0
Configuring the health check port to: 8080
[2026-06-27 02:34:29 +0000] [135] [INFO] Listening at: http://0.0.0.0:8080 (135)
starting syslog-ng
```

## Follow-up change made in this run

The pack harness was tightened so future Fortinet lab runs fail closed before replay unless the Splunk health check is executed as the Splunk user and the SC4S container has both a `syslog-ng` process and a bound TCP/20032 listener. The SC4S parser timestamp step was also simplified to avoid a conditional parser block around fixture-backed `date`/`time` values.

## Evidence boundary

This attempt proves only that the previous Fortinet disposable harness could report a healthy container while the intended SC4S listener was absent, and that fixture replay therefore did not reach SC4S/HEC/Splunk. It is not FortiGate/FortiOS appliance validation, SC4S movement evidence, HEC delivery evidence, indexed Splunk read-back, field validation, production readiness, or trust/quality promotion.
